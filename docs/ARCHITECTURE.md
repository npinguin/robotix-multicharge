## Purpose and ownership

Robotix MultiCharge is an independent Home Assistant integration for coordinating electrical charging. It starts with cars but can support other rechargeable mobility assets when their real charging capabilities are known.

| Logical object | Responsibility |
| --- | --- |
| `ChargeController` | One coordinated plan for a group of charge points and a configured charging power ceiling |
| `Charger` | The logical charge point, its supported controls, assigned asset and physical readback |
| `ChargeableAsset` | The object needing energy, its requested amount, target and Ready By deadline |

One Controller coordinates its Chargers. A Charger has an explicit MultiCharge Active/Inactive setting. A logical association is not evidence that a particular vehicle is physically connected or identified.

The original Home Assistant integrations keep ownership of the physical devices, source data and their entity IDs. MultiCharge exposes stable logical charging devices without copying or reparenting the source devices.

## Charging Asset type and effective charging power

**Owner clarification, 22 November 2026:** Keep exactly the existing three logical HA concepts: `ChargeController`, `Charger` and `ChargeableAsset`. **No separate Vehicle, Bicycle or other charge-domain module/device.** The existing `ChargeableAsset.kind` is the native, device-owned editable `select.kind` (car, bicycle, motorcycle, scooter, other), translated as **Asset type**. It is **taxonomy, not charging physics**: the same demand model, source qualifiers, charger electrical limits, physical writer and timetable serve all supported kinds. Do not infer SoC, connector availability, session identity, battery losses or specialized charge curves from the type. A bicycle can request kWh/duration without an OEM battery sensor. Additional type-specific capabilities need separate evidence and user approval; never silently branch the planner on a display label.

**One real power observation, two owned HA views:** The physical provider retains the authoritative `Charger.power_entity`, expressed as fresh W/kW and normalized once by the existing `source_evidence.number` reader. The existing Charger native power sensor `robotix_multicharge:charger:<id>:power` retains its Unique ID and projects this actual **charger-side** measured power. The new Charging Asset native power sensor `robotix_multicharge:asset:<id>:power` reuses the exact same `Evidence` object **only when** the one existing executor has a confirmed active session naming that Asset on the assigned Charger, and its current cable source is positively verified connected. A selected/saved assignment, hypothetical forecast, historic receipt or unknown connection is never sufficient proof for live Asset attribution. No second meter, device or separate charging-power estimation engine is introduced.

**Measurement semantics:** Both HA sensors are labelled **Effective charging power** in the supported languages, meaning *physically observed charger-side charging power at the selected measurement point*, **not** net DC power delivered to a battery or charge efficiency–adjusted storage power. The source entity ID, source timestamp, quality and attribution basis remain visible as entity attributes. If the source is absent, invalid, stale or not attributable, the sensor is **unknown/unavailable**, not a made-up zero or planned kW. A genuine source reading of 0 is preserved when supported and attributed. Asset projected kW becomes unknown as soon as the plug is disconnected, assignment/session provenance disappears or the source loses quality; Charger raw physical power remains independently reported. Existing Recorder history remains owned by the charger/source and cannot be relabelled by a later assignment. This is source-observation transparency, not a replacement for physical session commissioning.

**HA native ownership and languages:** Native Controls/Config/Sensors/Diagnostics stay on their owning Charger, Charging Asset or ChargeController. Existing generic `kind` remains the single asset type editor in the HA device's Config group; no parallel type settings or domain layer. The original five-view UX keeps short translated labels and shows asset type + the qualified power value. Eight native HA and card locales: **English, Nederlands, Français, Dansk, Norsk bokmål, Svenska, Deutsch, Español**. Translate HA entity keys/states without changing machine values, stable IDs, device association or existing Recorder semantics. Missing languages or mismatched keys fail developer tests.

**Explicit acceptance:** Test car, bicycle, motorcycle, scooter and other with the same `ChargeDemand` contract, and no-SoC kWh/duration case; current-plug attribution with a source of 2.3 kW, genuine measured 0 and missing/stale sources; assignment-only/forecast cannot claim asset power; unplug, session reassignment or restart hold removes the asset reading but never rewrites Charger history; German and Spanish entity/UX labels render under native HA; entity identity and Config Entry survive reload. **Source tests do not establish real HA rendering or EVSE/battery-side qualification.**

## Configuration

**Recommended:** one-click native Home Assistant Add Integration creates a valid empty Config Entry without a mandatory setup wizard. Optionally configure later from native HA **Devices & services → MultiCharge → Configure**, or the existing five-tab MultiCharge dashboard. The same settings and identities are shared.

**Expert:** the same canonical `controller/assets/chargers` configuration is prefilled in the native **Configure → Edit complete configuration (JSON/YAML)** and dashboard **Settings → Edit YAML** editors; both offer one direct Save to the **same** schema-validated Config Entry. No separate JSON file, Review wizard, imported shadow owner, parallel planner or physical charging action. File-owned imports retain their original ownership and cannot be overwritten from Configure; activation is handled by the ordinary Charger setting. Typed native HA Number/Select/Text/DateTime projections and in-dashboard owner controls stay available.

Illustrative expert configuration (shape is under development; not yet qualified in HA):

```yaml
# configuration.yaml
robotix_multicharge: !include multicharge.yaml

# multicharge.yaml
controller:
  id: home
  name: Home charging
  max_parallel: 2
  max_power_kw: 11
assets:
  - id: family_car
    name: Family car
    kind: car
    soc_entity: sensor.family_car_battery
    target_soc: 80
chargers:
  - id: driveway
    name: Driveway
    kind: variable_current
    rated_power_kw: 11
    phase_count: 3
    min_current_a: 6
    max_current_a: 16
    power_entity: sensor.driveway_power
```

Native one-time setup, legacy import validation and logical HA setup devices have been committed. Real HA dashboard configuration/reload and rollback still require qualification. Physical actuation is source-tested but remains gated by explicit activation, applicable constraints and capability-appropriate command readback.

### Full owning-object configuration projection (UC14-UX-OWNER-02)

The bundled standalone five-tab card is still one presentation consumer of the single validated Config Entry and native HA Registry. Site/ChargeController, ChargeableAsset/Guest and Charger each own one identity and all of their persisted fields. The same `configuration.py` canonical schema, `MC_OWNER_GROUPS` per-object UI projection and source-only drift check ensure a supported setting cannot be silently lost between schema and object Details. Fields absent from configuration display `Not configured` rather than fabricated defaults, and optional future keys show under the same owner's additional-settings group. Device-specific sources and applicable electrical limits and activation remain owned by their logical Charger/Asset/Controller and are edited through guarded typed fields in the existing MultiCharge dashboard, never through a second settings authority.

Native Site `solar_source_kind` and `grid_power_direction` Selects and the complete existing Controller energy-source Text entities fill previously missing source authoring paths. Source-kind transitions only admit an already selected required native sensor. The separate Guest/Vehicle card displays goals, source quality, locally scheduled weekdays, pricing and original charging history; Charger cards display activation, independent measured state, electrical source facts and per-session duration/energy/STOP receipt. A quick Overview goal or schedule action opens the **specific selected** Vehicle, not whichever asset comes first in the list. Real HA admin identity is checked by the backend for every native preference mutator, not only by hiding frontend controls.

No additional framework, separate HACS ApexCharts *add-on*, external runtime, source registry or parallel command writer was introduced. A passing source/isolated-HA check is not a real-browser, qualified provider or physical EVSE result.

## User experience and native entities

| View | Primary task |
| --- | --- |
| **Overview** | See what is charging, what comes next and what needs attention |
| **Charging Plan** | View today/tomorrow planned vs measured charging and readiness |
| **Chargeable Assets** | Manage energy needs, targets, deadlines and source quality |
| **Chargers** | See connection, assignment, capabilities and true hardware feedback |
| **Settings** | Guided setup, source mapping, strategy, limits and diagnostics |

The six requested modes are Automatic, Solar, Economy, Ready By, Force Charge and Off. A manual command still obeys the configured limits and physical equipment protections.

Expose stable native HA device and entity IDs for the three logical concepts. Ordinary HA dashboards and automations must remain possible even without a bespoke card. A dedicated chart is justified for the future interval timeline; no second planner or data store belongs in the frontend.

Logical identity and selected source bindings change only through deliberate structural edits. Live SoC, energy, current and availability updates never rebuild device registry topology. Missing and unknown must never be rendered as zero or as a successful charge.

## Beginner-first owner controls and Basic-inspired combined time chart

This is a **presentation-only reuse** of the proven Wessels Mobility Basic user hierarchy, not a dependency on Basic's site YAML or an external ApexCharts installation. The existing MultiCharge one-Config-Entry owner and `robotix_multicharge/get_plan` read-only WebSocket provide the only chart data, native HA Recorder actuals, tariff intervals and Charger/Asset IDs. The front-end renders a high-level real **kW** timeline with shaded proposed, outlined physically accepted, solid actually measured power and a separately scaled, basis+currency-labelled price line; it then lists dynamically generated, independently labelled Charger lanes with actual Vehicle association and source quality, including a separate clearly marked *indicative/not reserved* track.

The read view accepts `day=today|tomorrow|both`, with `both` as two local calendar days. The bounded query permits a maximum of 49 real hours because the fall DST day can contain 25 hours, while spring yields 47. There is no duplicated chart state or second native entity database; the frontend only visualizes already-qualified source, plan and Recorder results. Filtering affects the backend query and the visible chart/lanes; source-unknown historical power is never retroactively assigned to a newly selected vehicle. 0 and 10+ chargers are data-driven; no private Garage White/Black/Peblar/Utility IDs cross the public repository boundary.

A novice changes a charging goal using exactly one validated Asset revision (SoC vs finite kWh/minutes/EUR, leaving independent kW hardware caps untouched), schedules specific local day/time choices using the same native Calendar preferences, and reaches plan/goal/STOP from Overview. STOP is surfaced only through native `command_capabilities.stop_allowed`. Technical settings stay one explicit disclosure step within the same Asset/Charger instead of becoming a new interface or lost feature. HA admin versus read-only resident remains enforced by the existing backend. For acceptance semantics and real-HA/browser tests, see [UC14-UX-ROW-01](FUNCTIONAL_SPECIFICATION.md), Issue #1 and the current or latest merged PR.

## Charging plan timeline

A single responsive, bundled timeline will be usable at ChargeController level and filtered by Charger or ChargeableAsset.

- 15-minute slots for today and tomorrow in the HA timezone, including 23/25-hour daylight-saving days. A vehicle gets **active, executable-candidate** kW slots only when the Charger is physically connected and the vehicle identity has been verified or user-confirmed for the current plug session. A saved Charger preference is never connection proof. Disconnected vehicles may have **separate dashed, non-reserving what-if forecast slots** when a selected Charger and valid demand/capacity evidence exist; they never enter the active plan or authorize a command. Past actuals remain visible.
- Proposed plan, accepted plan and **measured** actuals distinguished, with power (kW), energy (kWh) and source freshness. Give the user a **Color by Vehicle / Color by Charger** identity toggle with stable colors derived from immutable IDs (never array index). Each Vehicle and each Charger has its own **user-changeable plan_color on its owning native HA Device**. MultiCharge assigns unique automatic defaults per owner category (Vehicle vs Charger); user choices persist across days, renames and reassignment. Encode Proposed/Accepted/Measured separately by opacity, stroke/pattern and explicit label, not a single shared color. The chart shows the selected vehicle **and** Charger for each slot, and does not double-count physical measured kW.
- Ready By and expected shortfall clearly indicated; optional electricity price and solar/context sources when available.
- A simple mobile view, accessible labels, readable legends and explicit unavailable/unknown states.
- Future slots queried through one bounded, read-only plan view; measured history from native HA telemetry and Recorder. A bounded equal-priority/deadline constrained-arrival/window retry reuses the same planner only if it covers additional goals without losing previously covered goals. Goal assessments and compact timeline windows are a read-only full-horizon projection. Power-binding epochs in the existing control Store prevent relabeling past measurements after remap; they are metadata, not a meter history database. Do not rewrite 48-hour plan arrays into giant sensor attributes or compute a new plan in the chart.

The source contains a deterministic 15-minute proposal planner, an admin-only bounded native HA query and one source-tested five-tab UI with separate proposed, accepted and actual signals. A single guarded actuator handles selected native switch and adjustable-current commands and 15-minute Automatic/Solar/Economy/Ready By execution; manual Force Charge and Off use the same writer. It requires explicit activation, goal-relevant sources, configured electrical constraints and appropriate command readback. The implementation now also includes native completed-session receipts, conservative tariff costing, an admin-validated Config Entry preferences editor, safe native STOP button, temporary guest expiry and stable historic session attribution. **Source and simulated HA-service tests are not actual HA/browser or actual hardware command/readback. Full session recovery, user permission scope, all five rendered views and complete UC01–UC29 end-to-end qualification remain OPEN.**

## Planning, physical execution and safety

```text
Native HA sources (charger, asset, price, solar, available site power)
    -> validated binding and source freshness
ChargeableAsset needs + Charger capabilities
    -> ChargeController: coordinated charging plan
    -> one authorized Charger actuator
    -> independent actual hardware readback
```

The configured power budget, circuit and charger limits are binding safety constraints, not soft suggestions. Missing or stale safety-critical capacity is never treated as unlimited. A verified on/off switch cannot be represented as variable-current control. A command acknowledgment is not proof of actual physical power change.

**Durable Pause/Resume (development candidate):** the existing Charger executor
records a per-Charger user pause hold in its existing native HA control Store
*before* attempting a physical STOP. The confirmed Pause response requires
independent physical switch/power readback. A failed or uncertain STOP remains
held and quarantined. Pause excludes the Charger from both firm and indicative
plans; it cannot be auto-restarted by the next quarter. Resume requires an HA
administrator, a qualified physically idle Charger and successful persistence;
it **only releases the hold**. A future eligible quarter or a separately
admitted manual START must pass the ordinary activation and safety
checks. The Charger native Pause/Resume buttons and the existing admin
WebSocket use this one path. A measured, physically closed session may clear
its former in-flight intent lock only after time-bounded receipt qualification;
unknown delivered energy retains the hold. Stored pauses survive a normal HA
restart, never restore a former active physical session. User journeys,
provider failures, native permissions and real-hardware readback remain
unqualified by source CI alone.

**Expert JSON (development candidate):** direct human-readable Controller,
Charger and ChargingAsset objects are mapped to the same canonical validated
Config Entry and HA source-import lifecycle. Only electrical bindings relevant to the chosen capability and configured limits are required. Imported JSON is still read-only from the native settings interface.

The installed equipment and built-in charger protections remain authoritative. MultiCharge enforces its own configured limits and reports its own command results.

## Current dev charging-calendar and finite-budget integration

The existing `ChargeableAsset` owns its **Ready By recurrence** and optional **allowed charging windows**; they are different constraints. `Specific days` with independent weekday clock values supersedes the resident-facing single-anchored Weekly option, preserving old settings via time-zone-aware migration. The Controller resolves next deadlines in site-local time, filters real UTC quarter slots against allowed windows and evaluates budget demand with source-qualified tariffs. All native daily preferences remain on the same logical HA Device and same validated Config Entry.

One `NativeSwitchExecutor` continues to handle every physical START/STOP. An asset or Charger-only finite request may be specified as measured grid kWh, duration or indicative variable EUR budget, but not several at once; adjustable Charger kW remains a separate hardware-capped control. Monetary execution needs an independent energy meter and non-spot *effective* tariff coverage; no billing ledger or external provider dependency is added. If meter timestamps cross distinct effective prices without a boundary energy reading, charge progress uses a conservative maximum-rate upper bound and labels it separately, stopping earlier if necessary. Source gaps hold/STOP instead of inventing financial evidence.

A protective cross-Charger STOP can dispatch while another Charger's unconfirmed START holds a long readback lock; the same-Charger command safety and subsequent independent STOP readback remain mandatory. This adds no scheduler, writer, new product layer or persistent financial ledger. **Source implementation/CI is distinct from feature-complete real browser/physical qualification**; authoritative acceptance belongs only to [UC05-BUDGET, UC06-SCHEDULE and UC22-STOP-LATENCY](FUNCTIONAL_SPECIFICATION.md).

## Upstream v2.6.1 behavioral parity without second price engine

The community implementation derives the original upstream `jonasbkarlsson/ev_smart_charging v2.6.1` observable charging strategies from the **existing** Asset, one Controller plan and one guarded executor rather than importing the old EVSC coordinator. A validated Asset controls `continuous_charging`, `earliest_start_at`, `minimum_soc_pct`, `maximum_price_per_kwh`, `price_currency`, `low_price_trigger_per_kwh`, `low_soc_trigger_pct`, `opportunistic_kind` (`off/type1/type2`) and `opportunistic_level_pct`. Logical HA Device native Select/Number/DateTime/Text entities and the bundled five-tab Asset editor write that same Config Entry. Existing settings, IDs, planned power semantics, device capability checks and the default split-quarter strategy are not rewritten.

The Controller picks cheapest qualified 15-minute slots or, when requested, one *actual consecutive* sequence fitting the same electrical, calendar and deadline limits. Target SoC and the explicitly verified minimum/low-SoC threshold are separate: only the bounded minimum energy may bypass a configured price ceiling. The low-price trigger can prioritize the eligible current slot; two opportunistic cap formulas reuse `qualified_price_policy_cap()`, shared by the pure plan and physical decision. The executor independently checks fresh current price, explicit currency, SoC, earliest start, connection, owner and physical readback at START and for a continued session. Price change, stale provider or loss of minimum-SoC authorization triggers guarded STOP rather than silently continuing on a stale proposal. Effective-price money budgets are distinct from spot-based economic ranking, have a **24-hour cumulative physical-and-planning safety limit**, and never imply a certified invoice.

**Safe non-parity boundary:** Original upstream's `Keep charger on` is *not* evidence that an independently controlled physical on/off Charger can precondition without further battery charging. Only a native hardware capability that independently proves safe preconditioning/supply (and qualified end condition) can close PARITY-11. Until verified, do not add a permanent `turn_on` override, second writer or misleading success state. Source tests/isolated HA checks do not qualify actual hardware, responsive browser. See the existing [canonical use cases](FUNCTIONAL_SPECIFICATION.md), [Issue #1](https://github.com/npinguin/robotix-multicharge/issues/1) and [PR #20](https://github.com/npinguin/robotix-multicharge/pull/20).

## Owner-approved extension: indicative disconnected-vehicle forecasting

**22 November 2026:** Owner permits **unplugged saved vehicles in the same Charging Plan as clearly separated forecasting only**. This extends, but does not weaken, the earlier connected-only **active** plan contract. No new device type, planning implementation, command writer, backend scheduler or sixth UI tab.

**One engine, two truths:** \`ChargeController\` builds the authoritative connected-eligible proposed plan first; only that plan is consumed by the existing executor. A second, **non-executable what-if assessment** runs through the SAME \`compile_plan\` algorithm with the connected proposals passed as already occupied quarter-hour slots. This preserves group kW, phase current, circuit current, parallel charger count, qualified solar/price and expiring binding envelope across both sets. Forecast demand can only use the **hypothetical residual**; it neither changes a real proposal nor holds/accepts capacity, alters dispatch priority, issues a service call or creates fictitious measured energy. The scenario is always labelled conditional; real arrivals invalidate and trigger refresh of the actual plan, not automatic promotion of an old forecast slot to accepted.

**Inputs/provenance:** A saved but disconnected Vehicle with a selected Charger, valid energy/duration/target demand and qualified disconnected source may appear as dashed indicative slots.
