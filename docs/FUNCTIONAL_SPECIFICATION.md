# Robotix MultiCharge — functionele productspecificatie en use-casecontract

## Approved functional baseline — 24 November 2026

MultiCharge charges a battery optimally using the supplied context, from a suitable on/off device and a finite guest duration to integrated SoC, adjustable current, solar, tariffs and multiple chargers. These are combinations of capabilities, not tiers or mandatory maturity stages. Keep one Controller, Charger and Chargeable Asset model, one Config Entry, one planner and one executor. This approved section supersedes earlier commissioning/certification and mandatory-context language where inconsistent; all unrelated functionality and acceptance obligations remain.

| User-facing property | Values | Authority |
|---|---|---|
| Activation | Active / Inactive | Explicit user intent; existing control_owner (multicharge / external) |
| Connection state | Asset connected / No asset connected / Unknown | Actual selected connection evidence; assignment is not connection |
| Charging session | Charging / Paused / Stopped / Unknown | Actual session/source evidence; switch ON alone is not charging |
| Charging state | Ready / Waiting / Error / Unavailable / Unknown | Existing runtime equipment/goal assessment, with reason and source quality |

Inactive retains bindings, intent, history and monitoring. Commissioning means initial configuration, not a separate verification state. Legacy physical_commissioned is a derived compatibility projection; old uncommissioned control never silently activates. Pause/Resume is an independent charger admission hold, not automatically a paused session. Existing physical source statuses, suspension/completion reasons, lifecycle/history, assignment, goal, strategy, plan, command outcome, quality and measured facts retain their meaning. Do not rename existing public identifiers or redefine Premium asset lifecycle. No new state engine/store or OCPP dependency.

Own what MultiCharge controls: explicit authorization, applicable constraints, commands, persistence/reconciliation, truthful feedback. User supplies suitable hardware, mappings and limits; hardware retains electrical protection. No certification of external controllers. A finite duration request using a suitable switch works without invented cable/SoC/power/energy/phase/tariff inputs; switch readback confirms output only. Selected physical fault/disconnect and relevant constraints still matter. kWh, budget, SoC and adjustable-current goals use the evidence actually necessary for that goal. No silent fallback of an explicit objective. Inactive does not send new commands after safe reconciliation. MultiCharge is responsible only for its own configured commands, goals, observations and applicable constraints. The user selects the endpoint and activation. Other charging products, site migration, controller discovery, coordination, transfer and cross-product rollback are outside MultiCharge scope and are not product, TEST or STABLE acceptance conditions.

For assigned or anonymous finite on/off duration without a selected connection source, use the explicit user assignment/intent for admission; keep connection and physical battery identity unknown, with a switch-output duration receipt, not measured battery charging. Selected connection evidence and actual disconnect still constrain execution. A direct SoC stop uses observed SoC and target; capacity and efficiency are necessary for energy/deadline estimation, not direct target closure. Adjustable native number metadata supplies missing range/step; configured bounds remain constraints. Declared conversion and qualified native setpoint plus measured power can support adjustable control without an independent current sensor, with no claim of measured amps. Applicable selected phase/circuit constraints remain binding.

## 0. Productvisie en toetsbare ontwerpgrenzen

**WHY —** Eén begrijpelijke laadervaring voor woningen met uiteenlopende laadpunten, voertuigen, prijzen, zon en gedeelde elektrische capaciteit zonder foutieve planning of meerdere fysieke commandowriters.

**WHAT —** Eén onafhankelijke Community Home Assistant-integratie met **ChargeController, Charger en ChargeableAsset**, vijf vaste schermen (**Overview → Charging Plan → Chargeable Assets → Chargers → Settings**), native configuratie, laadplanning, source-quality, uitvoering/readback, historie en herstel. Zonder verplichte Robotix Core/Basic/Premium, site-packages, template-sensors of handgemaakte helpers.

**HOW —** Hergebruik native HA-providerdata, Entity/Device Registry en Recorder. MultiCharge normaliseert geselecteerde bronnen, bezit één Config Entry, één 15-minutenplanner, één guarded executor en één resident/admin-UX. Bronmetingen blijven bij hun native provider. De gebruiker configureert en activeert de gewenste native aansturing; MultiCharge beheert uitsluitend zijn eigen opdrachten en feedback.

**PROOF —** Per UC een reproduceerbare GIVEN → WHEN → THEN, negatieve/fail-closed proef en waarneembaar bewijs. Developer/source CI, echte HA-integratie, browser, leverancierreadback, fysieke EVSE en field acceptance worden afzonderlijk vastgesteld. Een servicecall is geen fysiek resultaat.

**NEXT —** Volledige ontwikkelscope en regressies afwerken, daarna de bestaande kwalificatiepoort doorlopen met echte 0/1/2/4/10 laadpunten, nacht-/DST-tijdvakken, 390/1024/1600 schermen, acht talen, hardware en rollback. Geen stilzwijgende scopeknip of productiecutover.

### 0.1 Gebruikerservaring en configuratie — eigenaarbeslissingen (23–24 november 2026)

**Eén Config Entry, twee native bewerkpaden.** Home Assistant **Add Integration** maakt meteen een geldige lege MultiCharge Config Entry aan: zonder verplichte Charger, ChargeableAsset, prijsbron, PV-meter of setupwizard. **Home Assistant → MultiCharge → Configure** opent steeds een echte, optionele Home Assistant Options Flow met **Charging site / Chargers / Chargeable assets / Energy & prices / Expert full configuration**; de bestaande getypeerde velden in het vijf-tab MultiCharge-dashboard blijven daarnaast bestaan. Beide paden wijzigen exact dezelfde Config Entry. Geen los te installeren YAML/package, heraanmaak van Config Entry of dashboard-only omweg. De directe vehicle-keuze, 80%- of andere laadbehoefte, Ready By, laadmodus en veilige STOP blijven zichtbaar zonder technische fold; alle overige source-/elektrische/activatievelden zijn binnen hetzelfde owning object bereikbaar. Voertuigen en laadpunten kunnen daar toegevoegd, gewijzigd en verwijderd worden. De ene gevalideerde Home Assistant Config Entry blijft de persistente eigenaar; native HA Devices/Entities blijven interoperabele projecties.

**Complete configuratie zonder extra UI-poorten (eigenaarcorrectie 24 november 2026).** **Settings → Edit YAML** toont altijd de volledige bestaande configuratie en biedt **één grote textarea, Save en Cancel**. Geen voorafgaande Review, importwizard, dubbele invoer, simulatie, frontend-rolfilter dat de editor stilzwijgend verbergt of andere extra klik om SAVE mogelijk te maken. De bestaande getypeerde velden blijven beschikbaar. Bij Save stuurt de client de volledige data-only JSON/YAML met de origineel geladen revisie naar de **bestaande** Home Assistant Config Entry; server-side admin-autorisatie, schema-validatie, concurrency-check en de bestaande controles voor eigen opdrachten en sessies onder executor-lock blijven onverkort gelden. Een afwijzing toont de concrete reden zonder de getypte tekst te verliezen; bevestiging volgt op feitelijke Config Entry readback. Bron-owned historische YAML blijft source-owned en wordt niet overschreven; activatie is een gewone gevalideerde Charger-instelling. Geen extra configuratiestore, package, helper, template of parallelle laadsturing.

**SAVE, bewijs en veiligheid.** Elke getypeerde of rechtstreeks opgeslagen complete YAML/JSON-wijziging passeert echte HA admin-autorisatie, schema- en Config Entry-revisiecontrole, de bestaande executor-lock en relevante controles op eigen sessies, bronnen, limieten en configuratiewijzigingen. Pas na authoritative readback mag SAVE bevestigd worden; mislukking of timeout leidt niet tot een fictieve verandering of fysiek START. Acceptatie vereist positieve/negatieve taken voor 0/1/4/10 Chargers/Assets, add/edit/delete, alle ondersteunde bronkeuzes en settings, role denial, persist/restart/rollback en echte Chromium op 390/1024/1600..

### 0.1.1 Progressieve capability — bijna geen informatie tot volledige bronintegratie

**Acceptatieprincipe:** MultiCharge is één generiek product met **capability-driven progressive enhancement**, geen aparte Lite/Pro-mode, geen nieuwe Charger- of voertuigklasse en geen verplichte databronlijst. Je kunt een lege laadlocatie, een Guest zonder OEM/SoC en een eenvoudige geschikte laadmogelijkheid toevoegen **zonder** prijzen, PV, Energy Dashboard, andere Robotix-producten, YAML-packages of template sensors. Een extra, gevalideerde bron ontsluit alleen de functies waarvoor die bron nodig is. Een ontbrekende bron mag **niet** een onafhankelijk bruikbare functie uitschakelen; zij mag ook geen fysiek veiligheidsbewijs simuleren.

| Installatieprofiel | Welke gegevens zijn werkelijk beschikbaar? | Wat de gebruiker moet kunnen doen | Niet zomaar toestaan / vereiste kwalificatie |
| --- | --- | --- | --- |
| **0 — Nieuwe of lege HA** | Geen voertuig, geen Charger, geen OEM-account, geen PV of tarieven | Integratie configureren, drie logische concepten begrijpen, lege vijf-tab UX zien, later bronnen en apparaten toevoegen | Geen fictieve verbonden Charger of fysiek START |
| **1 — Guest + eenvoudige, elektrisch geschikte smart plug/aan-uit-lader** | Guest of geen geregistreerd voertuig; geschikte native aan/uit-service, eventueel gemeten vermogen; geen SoC of kabelsensor | Eindige minuten laden met echte outputstatus, later extra bronnen toevoegen | Gebruiker kiest geschikte apparatuur en activeert MultiCharge. Switch-readback bevestigt output, niet batterijvermogen of verbinding. Geselecteerde bronnen en toepasselijke limieten blijven bindend. |
| **2 — Charger met echte energie- en statusmetingen, maar geen OEM-SoC** | Native connected/disconnected of bewezen equivalente status, gemeten W/kW en kWh; on/off of gekwalificeerde current | Eindige kWh-/minutenlading, actuele sessie, gemeten progress, prioriteit en deadline; Economy/Solar alleen bij echte optionele sources | Geen kWh-claim uit tijd alleen; `switch.on` is nooit een kabelmeting; geen fictieve resterende batterijlading |
| **3 — Volledige native Charger + voertuig + energiebronnen** | Bijvoorbeeld VW ID.4/Audi Q8 met actuele OEM-SoC/health/capaciteit; Wallbox/Peblar met native connectie, vermogen, current set/readback; eventueel PV, grid, tarieven | 80%-default waar toepasselijk, eigen SoC-doel, Ready By, Automatic, Solar, Economy, current modulation, betrouwbare historie, kosten uitsluitend bij effectieve tariefdekking | Geen fabrikantcode in generieke planner, geen verplicht voertuigcloudaccount, geen afgeleide all-in kost uit spotprijzen, geen fictieve bevestiging van fysieke opdrachten |

**Eén betekenis, één eigenaar:** De native HA-provider bezit de fysieke service, het echte apparaat en zijn metingen; **Charger** bezit het fysieke laadpunt, de geselecteerde voertuigvoorkeur, geobserveerde aansluiting, veilige command-/readbackstatus en zijn gemeten laadsessie; **ChargeableAsset** bezit uitsluitend type/naam, optionele SoC, doel, duur/kWh, deadline/Guest-expiry en bewezen aan dat voertuig toe te schrijven progress; **ChargeController** bezit het gezamenlijke elektrische budget, de strategie, de planner en de geaggregeerde waarheid. Zie de definitieve ownershipmatrix in §2 — dit is geen vierde eigenaar of tweede configuratiesysteem.

**Wat onbekend mag zijn:** SoC, voertuigfabrikant, capaciteit, prijs, PV, thuisverbruik, forecast en zelfs een voertuigprofiel zijn **optioneel voor de toepasselijke eenvoudige workflows**. Wat nooit wordt gegokt: elektrisch veilige belasting, actuele fysieke connector waar nodig, passende command-/STOP-readback en geldige geconfigureerde site/circuitlimiet. De UI toont beschikbare acties en noemt de specifieke ontbrekende voorwaarde; geen globale Off-stand als vervanging van werkelijk ondersteunde functionaliteit.

**Twee representatieve generieke acceptatieprofielen (beide verplicht vóór Feature Complete):**

- **Minimale site:** schone HA, één geschikte on/off Charger, nul profielen of een Guest zonder SoC, geen PV/prijzen/Robotix-entities. Activeer, vraag eindige duur aan, observeer native switch START en tijdige STOP; onbekende verbinding, vermogen en kWh blijven onbekend. Test ook Inactive, ongeldige duur, afgewezen native opdracht en geselecteerde disconnect.
- **Rijke site:** schone HA, ≥2 verschillende native Chargers (Wallbox/Peblar of equivalente providers), Audi Q8/VW ID.4 of generieke OEM-SoC-bronnen, net-/PV-/prijsmetingen, 1/2/4/10 capaciteitscases; dezelfde drie Devices, dezelfde vijf-tab UX, één settings authority en één Executor, met extra bruikbare optimalisaties.

**Minimale site — zichtbare bediening en blokkering (UC05/11/17, UI-OWNER-10):** De Charger-view biedt één eindige duur of gemeten kWh. Niet-ingediende invoer blijft behouden bij refresh en wordt niet uitgevoerd. Een geschikt actief on/off toestel met alleen native switch ondersteunt eindige duur; gemeten kWh vereist een energiemeter. Inactive, ongeldige doelen, toepasselijke limieten, geselecteerde onbetrouwbare bronnen of verkeerde modus geven een concrete reden zonder ongeautoriseerde servicecall. Verwijderen/herbinden of gewijzigde revisie maakt een ongeldige draft ongeldig. Gebruik dezelfde executor met passende START/STOP-readback.

**Persistence-recovery contract (UC23/26/29):** Een native HA control-state snapshot moet vóór toepassing volledig en transactioneel gevalideerd worden: completions, inflight, pause holds, accepted slots en session receipts worden pas samen geadopteerd nadat de gehele payload veilig is. Een beschadigde *latere* ontvangst mag geen gedeeltelijke intent-, pause-, geschiedenis- of grantwijziging veroorzaken; START blijft in HOLD tot expliciet gecontroleerd herstel. Toets een snapshot met geldige eerdere velden maar ongeldige laatste receipt, en controleer zowel onveranderde bestaande history/holds als nul fysieke writes en een ondubbelzinnige fouttoestand. Geldige historische IDs blijven op restart behouden; nooit een fysiek actieve sessie herstellen.

**UC-ankers:** UC01/02 (installeerbaar zonder bronnen), **UC05** (finite en zonder SoC), **UC11** (geschikte on/off / smart plug), **UC12** (volwaardige current capability), **UC13** (Guest), **UC17–20** (optionele, afzonderlijke inputkwaliteit) en **UC21/22/24** (niet-onderhandelbare fysieke veiligheid). FLEX-01/03/04/10/11/19 en UI-OWNER-05/10 toetsen deze exacte variatie. **Documentatie definieert de doelwerking, niet dat de huidige dev-bron deze minimumsite al fysiek accepteert.**

**BUDGET-07 — Tariefgrens binnen één meterdelta:** Wanneer onafhankelijke cumulatieve kWh-meterstanden een interval bestrijken dat werkelijk over meerdere volledig gedekte `effective` tariefvakken loopt, kan MultiCharge zonder deelmeterstanden **niet** de exacte kWh-verdeling per tarief bewijzen. Om de sessie bruikbaar én veilig te houden, telt de Budget Supervisor dan een **conservatieve bovengrens**: de werkelijk gemeten hele energie-delta × het hoogste niet-negatieve effectieve tarief over alle volledig aaneengesloten vakken in die delta. Deze bovengrens wordt ondubbelzinnig als `conservative_upper_bound` gepresenteerd, niet als betaalde kosten, factuur of exacte prijs. Ontbrekende, overlappende, vreemde valuta of onbetrouwbare intervaldekking => stop/HOLD, geen nulprijs of afgerond fictief budget. Drempelbewaking gebruikt de conservatieve opgebouwde kost, dus kan vroeger STOPpen. Bij de sessiereceipt blijven exact gemeten kWh en indicatieve conservatieve budgetkost gescheiden. **Negatieve test:** twee effectieve tarieven €0,20/€0,40 per kWh met 1 kWh ongesplitste meterdelta => maximaal €0,40 aan gereserveerde budgetruimte, niet fictief een exacte €0,30. ### UC06-SCHEDULE — Specifieke weekdagen en lokale laadtijden (2026-11-23 owner clarification)

### UC07-PARITY — Upstream individuele laad- en prijsstrategie behouden
**Vergelijkingsautoriteit:** originele upstream `jonasbkarlsson/ev_smart_charging` stabiele v2.6.1, **niet** onze V2-fork. **`PARITY-01`** één voertuig/Charger kiest goedkoopste kwartieren zonder groepsinterferentie; expliciete keuze continu/niet-continu blijft betekenisvol waar hardware dit ondersteunt. **`PARITY-02`** configureer minimum SoC, een echte prijsgrens en low-SoC/low-price triggers met duidelijke voorrang en fysieke veiligheidsgrenzen. **`PARITY-03`** optionele opportunistische prijsstrategie wordt transparant toegepast of de gelijkwaardige productstrategie wordt expliciet geaccepteerd; geen verborgen verlies van prijsgedrag. **`PARITY-04`** vroegste laadstart, einde/Ready By en onhaalbaarheid zijn zichtbaar én begrenzen de planner. **`PARITY-05`** preconditioning/Keep charger on krijgt expliciete veilige productbeslissing en hardwaregeschikte uitvoering zonder heimelijk veiligheidsgrenzen/stopvoorwaarden op te heffen. **`PARITY-06`** alle positieve/negatieve upstream-prijs-, SoC-, DST-, fysieke readback- en restartregressies doorlopen tegen exact bronversie voordat migratie GO is. Als een functie nog niet is geïmplementeerd: `OPEN`, niet zeggen dat andere modes al parity bewijzen.

**PARITY-07 — Continuous window example:** Price slots 00:00 (€0.05), 00:15 (€0.90), 00:30 (€0.05), 00:45 (€0.90), 01:00 (€0.05), 01:15 (€0.05) with a physically fixed 4 kW Charger needing 2 kWh. **Non-continuous** may select 00:00 + 00:30; **continuous** selects the cheapest *consecutive* 2 slots (01:00 + 01:15). Both obey shared group/phase/circuit limits, valid timestamps, a real Ready By and one executor. If no consecutive feasible slots exist, show `CONTIGUOUS_WINDOW_UNAVAILABLE` and no fabricated success, without blocking other independent Chargers.

**PARITY-08 — Price limit vs minimum SoC:** Target 80%, current 25%, minimum 30%, price cap €0.20/kWh, observed effective spot €0.30/kWh: controller may schedule enough **physically safe** measured energy to reach minimum 30% even above price cap, but may **not** schedule the rest toward 80% at €0.30 unless an explicit low-SoC or price trigger applies. Unknown/expired/mixed-currency price or stale SoC cannot silently bypass cap. Minimum percentage is not an OEM SoC write.

**PARITY-09 — Immediate low price / low SoC:** A threshold of €0.10/kWh makes a valid available current quarter at €0.08 start earlier than the nominal cheapest later period, but never overrides safety/budget identity. **PARITY-11 — Optional preconditioning:** Original upstream's Keep charger on means leaving a qualified charger energized after reaching target to allow vehicle preconditioning. ### UC22-STOP-LATENCY — Fysieke STOP mag niet achter andere START-readback blijven wachten
**WHY:** De ene bestaande Controller-Executor beschermt concurrerende START-acties met een globale lock; de huidige implementatie wacht binnen die lock tot 45 seconden op fysieke readback. **ACCEPT / `STOP-LATENCY-01`:** Twee gecommissioneerde MultiCharge-laadpunten A/B. A heeft een fysiek onbevestigde START waarvan de native service wel is gestuurd en readback nog wacht. De gebruiker vraagt een STOP voor reeds actieve B. De native B-STOP moet **onmiddellijk kunnen worden verzonden zonder de volledige readback-timeout van A af te wachten**, en blijft `pending` tot B onafhankelijk fysiek 0 W bevestigt. Geen onbewezen `confirmed`, geen verhulde tweede writer en geen fysieke aansturing van Charger A door B's STOP. Bij hoge vertraging of falende B-readback wordt status `execution_unknown`, nooit een fictieve STOP.

**NEGATIVE / `STOP-LATENCY-02`:** Concurrente STOP op **dezelfde** Charger met nog open START/readback, tegenstrijdige current-service, Inactive, herstart en dubbele request-ID laten geen ongeautoriseerde bypass, replay of parallel START toe. Behoud de ene executor, oorspronkelijke native controles, gecontroleerde sessie-evidence en het groepsbudget. Geen generieke lock-verwijdering of tweede command-gateway. Bewijs met echte async HA-services/tests plus daarna echte hardwarelatentie vóór field GO.

**Owner instruction:** every supported physical or settings SET/action must have an independently observable native Home Assistant state on its **owning logical Device**, plus an authoritative **ChargeController-wide readout** updated **near-real-time**. This is an acceptance invariant of the existing UC01–UC29 and FLEX-01–FLEX-20, especially UC11, UC12, UC14, UC16, UC21, UC22, UC24, UC25, UC26 and UC29, not an additional implementation owner, database, physical controller or new workflow.

**Required canonical mapping (sensor names represent native logical entity capability; HA may assign entity IDs on installation):**

| SET/action | Primary concept / confirmation | Controller-level observable |
| --- | --- | --- |
| Mode SET | ChargeController: validated mode reloaded from Config Entry; never claim success on request alone | \`Charging mode\`, \`Settings revision\`, \`Last settings action\` expected/observed revision |
| Site max kW, phase limits, max parallel, source selection | ChargeController: authoritative site config and qualified source capacities, not estimated available power | \`Settings revision\` attributes, \`Plan status\`, independently measured total \`Actual power\` |
| Vehicle kWh/duration, target SoC, priority, Ready By, Guest expiry | ChargeableAsset: \`Charging intention\` + observed qualified battery/quality; no physical actuation implied | \`Last settings action\` scope/target/fields + \`Settings revision\`, \`Plan status\` on recomputation |
| Charger/Vehicle assignment, including No vehicle and idle-only switch | Charger: \`Selected vehicle\` (saved assignment), distinct \`Connection\` (physical); Asset derives its selected Charger | \`Last settings action\` and \`Settings revision\`, \`Connected chargers\` with true physical source quality |
| START, STOP, protective STOP | Charger: \`Command status\` requested→confirmed/rejected/execution_unknown and independently observed physical power/STOP | \`Last physical action\` with source Charger/request/readback/reason, \`Action health\`, \`Charging chargers\`, \`Actual power\` |
| Set adjustable current | Charger: \`Confirmed current setpoint\` vs separate independent \`Actual current\` sensor, source quality/time | \`Last physical action\`, \`Action health\`, actual aggregate kW and plan status, never request=current assumption |
| Physical connect/unplug/offline/stale | Charger: native Connection/power/current sensor with observed_at/quality; ChargeableAsset does not fake identity | \`Connected chargers\`, \`Charging chargers\`, \`Actual power\`; unknown is not 0; safe action health/hold |
| Quarter-hour plan allocation / deadlines | Controller: source-backed \`Plan status\` and bounded plan query; Charger/Asset states remain owner projections | \`Plan status\`, proposed vs accepted vs measured only from qualified evidence; no giant 48h sensor attribute |

**Near-real-time, source-first behavior:** subscribed HA sensor state-change and executor request/physical confirmation events should publish the updated logical and aggregate HA sensor values without relying on a page refresh or the 60-second fallback timer. Operational *target* for exact HA/browser qualification: **≤2 seconds from a locally observable HA source or accepted command outcome to emitted owner+controller state-change**, independently timestamped; physical EVSE/provider confirmation can take longer and **remains pending/unknown until fresh readback**. No guaranteed subsecond physical completion when hardware/provider is slower. Settings updates are only \`confirmed\` when the newly loaded Config Entry revision matches the requested revision; \`accepted_unconfirmed\` on pending reload, \`rejected\` on invalid/unsafe change. Source \`observed_at\`, requested_at, readback_at, request correlation, freshness and quality travel to sensors.

**Safety and consistency checks:** 0/1/2/4/10 Chargers; first successful action and rejected same action; concurrent independent Chargers; unknown/disconnected source, physical on/off mismatch, current feedback late, source stale, provider unreadable, persistence/restart hold, rejected/failed settings reload, idle reassignment without stopping unrelated Charger, Guest, absent vehicle, error/rollback. Aggregate connected count becomes **unknown** when one required connection source lacks quality; aggregate charging count and actual power become **unknown** on incomplete independent power coverage. A real measured 0 is 0; no inferred 0. Persistent canonical logical IDs must not change on name/assignment changes; vendor HA devices retain their original entities and history. Source tests are not installed HA timing, real EVSE, mobile/browser or complete UC acceptance.

## 4. Indicatieve forecasting zonder reservering of uitvoering

### Functionele uitbreiding: configurable Vehicle–Charger labels and strictly indicative disconnected forecasting

**Latest owner clarification (same chat, replaces the overly broad statement "unplugged vehicles have no future bars"):** Only physically connected and current-session-confirmed vehicles are eligible for **active, executable-candidate** proposed/accepted charging slots. However, the existing **Charging Plan** is allowed to show **clearly segregated, non-binding and non-executable indicative what-if forecasts** for registered vehicles not yet connected. The two layers must be calculated and visually labelled differently. The requested default identity label is **Vehicle + Charger**, e.g. "Audi Q8 · Wallbox White", with user-configurable **Vehicle / Charger / Both** and independent **Color by Vehicle / Charger**. No new tab, domain device, planner, controller or physical owner.

**Rules:** Use the one Controller planning engine and run active demand allocation first; only then simulate hypothetical disconnected demand using **residual** site/phase/circuit/max-parallel electrical capacity after those active quarters. Forecast is allowed to reflect user-entered expected plug-in time (\`expected_connection_at\`, ISO time with timezone); otherwise show the explicit assumption "**if connected now**" (never infer arrival probability or actual cable state). Future connected/confirmed requests always win; indicative slots never reserve group kW, affect active scheduling, become physically accepted slots, enter command/grant/replay logic, or produce actual energy/cost. Forecast must be excluded when cable quality is unknown (not proven disconnected), demand/source/capability missing, deadline infeasible or mode Off, with truthful non-numeric reason. All guest expiry and per-asset/charger uniqueness rules still apply.

**UX and native contract:** The existing 5-tab Charging Plan shows a visible per-Charger timeline and actual selected Vehicle–Charger combination, with named identity-colored planned/accepted/historic status and a **dashed/transparent labelled "Indicative – not connected"** row that cannot be confused with real charging. The selected fields \`plan_label_mode=vehicle|charger|both\`, \`plan_color_by=vehicle|charger\` and \`show_indicative_forecast=true|false\` belong to the existing controller Config Entry authority (not frontend-only hidden persistence). Display qualified price as independently scaled context only. Show real past physical power from Recorder under Charger; only attribute it to a specific Vehicle when a **session-time confirmed receipt** proves that interval, NEVER using today's selected vehicle. Return \`forecast_slots\` separately from active \`slots\`, with \`status=indicative_only\`, \`may_execute=false\`, \`reserves_capacity=false\`, bounded assumptions and forecast reasons. Only a compact forecast summary belongs on the native Controller \`Plan status\` sensor.

**Executable acceptance extension mapped to existing UC04/05/06/07/08/09/13/14/15/16/18/19/20/21/24/26/28/29:**

## 5. Per-device native voorkeuren, kleuren, labels en talen

### Functionele UX-eis: native preferences, per-device colors and short multilingual labels

**Owner instruction:** EVERY regular preference is edited through its native HA `select`, `number`, `datetime` or `text` on the correct existing **ChargeController**, **ChargeableAsset/Vehicle** or **Charger** Device. The five-tab card consumes these exact Registry entities; **no parallel Option Flow setter, cloned data store, JS-local setting, second physical writer, fake Charger entity or additional logical Device**. Expert source binding and applicable electrical limits remain ordinary validated configuration.

**Exact owner / state contract:**
- **ChargeController**: Mode, color dimension (Vehicle or Charger), label mode (Vehicle, Charger or Both, default Both), Forecast visibility native Selects; site maximum kW, maximum concurrent Chargers native Numbers; site name native Text. Plan and physical outcome diagnostics remain source-backed read-only native sensors.
- **Each Vehicle/ChargeableAsset**: its own `plan_color` Select, vehicle type, recurring Ready By Select; target SoC, requested grid kWh **XOR** duration, priority, max charge kW, battery capacity, efficiency native Numbers; Ready By, expected plug-in, Guest expiry when applicable native DateTimes; name native Text. Unassigned/unplugged Vehicle remains a full HA Device, does **not** receive active future slots.
- **Each Charger**: own `plan_color` Select, `Selected vehicle` Select including `none`/No vehicle, and name Text. Physical connection is a **separate** source-qualified native Binary Sensor; current and power remain Charger-owned measured evidence, never inferred from selected Vehicle. Changing selected car preserves one authoritative `charger.asset`; a car cannot be selected on two Chargers. Idle-only reassign never stops unrelated Chargers; unsafe/busy physical state refuses changes.
- **Color defaults**: Automatically unique, stable palette per owner category (Vehicle vs Charger, at least 10 of each), independent of order, rename, reassignment, Today/Tomorrow. User may explicitly override to any permitted color; persist that override on the correct Device via the one Config Entry authority, not in frontend memory. Match plan identity colors to the owner native select even for clearly separated dashed **Indicative** disconnected forecasts. Actual physical samples without proven vehicle identity remain neutral in Vehicle-color mode.
- **Translations / statuses**: User-facing labels are compact and comprehensible, not programmer comments, source enum strings, request-ID/error-code banners or multi-sentence instructions. Native HA select/number/datetime/text/sensor titles use translations (EN/NL/FR, plus DA/NB/SV native HA locales if translations exist); the bundled card has EN/NL/FR short labels. Backend machine enums and reason attributes can remain stable for existing automations, but ordinary visible state is localized when HA translation contract allows. Screen readers get the meaningful text as well as color/pattern; explanatory diagnostics stay in HA device details.
- **Access/safety**: These entity changes use exactly the same validation/revision/HA Config Entry and guarded executor lock as before. Display-only palette/label/forecast settings must not reload/STOP a charging EVSE. Physical limits, target/intent and pairing require the existing fail-closed safety gates. A completed service call is not positive physical confirmation.
